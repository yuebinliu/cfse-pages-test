总览技术栈优点

技术栈

全部建立在「Cloudflare 四件套 + WordPress」之上，没有额外的服务器。

边缘运行时

组件承担什么关键点
Workers路由、列表页渲染、REST 兼容层、后台 API免费档 10 万请求/天；每请求 CPU ≤10ms，await I/O 不计
D1文章/分类/用户/风格/应用密码SQLite；posts.wp_id 主键，列表页查询走它
R2单页 HTML、媒体、主题资源S3 兼容；出站流量免费；对象名 = 解码后的原文
KV站点上下文、缓存、风格激活态强一致读；写/删 1000 次/天（低频配置用它）

WordPress 侧

机制用途
save_post 钩子发布/更新时按三个开关分派：同步 D1 / 生成静态 / 上传远端
the_content 过滤器Markdown 渲染（vendored Parsedown，safe mode）
渲染三条路径内部模板渲染 / 前台抓取（100% 还原）/ 硬编码降级，逐级回退
REST 兼容层Basic Auth + 应用密码（SHA-256 盐哈希，避免 PBKDF2 的 CPU 开销）

渲染与协议

  • Markdown：Worker 端 marked、WP 端 Parsedown，两端输出对齐；md 原稿原样存库（content_format='md'）。
  • AWS SigV4：自实现签名（含 % 必须编码为 %25 的真机修正），用于直传任意 S3 兼容对象存储（R2 / B2 / Wasabi / MinIO…）。
  • 认证分层：后台 JWT、Worker 接口 X-Auth-Key、第三方编辑器 Basic Auth；限速用内存滑窗（0 KV 成本）。
  • key 规范：存储 key 一律为「解码后的原文」—— 写入解码、读取解码、URL 返回时逐段编码，三者一致才不再出现中文 404。

托管抽象

capabilities（要做什么） → r2 / d1 / render / cache transport（走哪个协议） → worker-api / s3 / fs / git 实现按 transport 分派 → 同一份产物目录，发给"具备该能力"的目标

没有目标具备某项能力时，该步骤被跳过且不联网（纯静态档因此天然成立）。
